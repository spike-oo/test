# 01 项目概述与技术架构

> 依据《第8组_智能AI校园外卖平台需求分析文档_按最初计划修订版_v3.docx》整理，供开发阶段查阅。
> 需求正文以需求文档为准，本文只做工程落地口径的说明。

## 一、系统定位

面向高校校园的 PC Web 外卖业务原型系统。核心服务对象是学生、校内商户和平台管理员；
模拟骑手配送作为可选加分功能，在核心功能稳定后再实施。

不做：真实支付、真实骑手硬件与定位、本地大模型训练、生产级资金结算。

## 二、分层架构

系统自下而上分为四层，与需求文档图 2-1 一致：

| 层次 | 职责 | 工程落点 |
| --- | --- | --- |
| 前端展示层 | 学生端、商户端、骑手端、管理员端界面 | `frontend/src/views/{student,merchant,rider,admin}` |
| 业务服务层 | 用户/店铺、菜品/订单、骑手/配送、评价/客服、饮食分析 | `backend/.../modules/*` |
| AI 能力层 | 语义理解、智能推荐、智能客服、评价分析、经营分析 | `backend/.../modules/ai` |
| 数据存储层 | MySQL 业务数据、Redis 缓存、对象存储、日志与审计 | `database/` + `config/RedisConfig` + 对象存储客户端 |

分层约束：

1. 上层依赖下层，禁止反向依赖；同层模块之间通过 Service 接口调用，不直接跨模块访问对方 Mapper。
2. AI 能力层不直接写业务表，只通过业务 Service 读写，保证业务数据只有唯一写入方。
3. 前端不直接调用大模型，所有 AI 请求经后端 `ai` 模块转发。

## 三、技术选型与理由

| 选型 | 理由 |
| --- | --- |
| Spring Boot 3 + Java 17 | 课程基线技术栈，生态成熟，便于分工并行开发 |
| MyBatis-Plus | 单表 CRUD 免写 SQL，复杂统计仍可落 XML，兼顾效率与可控性 |
| Vue 3 + Element Plus | 组件丰富，四端可在同一工程内按路由分区，降低协作成本 |
| MySQL 8 | 业务数据关系清晰、事务支持完善；文档要求 5.7+，本工程按 8.0 开发 |
| Redis | 热点缓存、抢单池、分布式锁三处使用，是并发难点的关键依赖 |
| WebSocket | 订单状态推送与骑手订单大厅广播，延迟要求 ≤ 2s / ≤ 1s |
| JWT + RBAC | 四种角色权限隔离，避免服务端会话状态 |
| 公有大模型 API | 不训练本地模型，通过统一客户端封装，支持配置切换模型 |

## 四、后端分层约定

```text
Controller  →  只做参数校验与响应封装，不写业务逻辑
Service     →  业务逻辑、事务边界、跨模块编排
Mapper      →  数据访问，单表用 MyBatis-Plus，复杂统计写 XML
Entity/DTO  →  数据库实体与接口出入参分离，不把 Entity 直接返回给前端
```

统一响应体（`common/api/Result.java`）：

```json
{ "code": 200, "message": "success", "data": { } }
```

- 业务成功 `code = 200`；参数错误 `400`；未登录 `401`；无权限 `403`；业务异常 `500`。
- 业务异常统一抛 `BusinessException`，由 `GlobalExceptionHandler` 转换为响应体。
- 分页统一使用 `PageResult<T>`，字段为 `total`、`pageNum`、`pageSize`、`list`。

## 五、订单状态机

订单状态是系统的核心数据，状态流转由 `modules/order/OrderStateMachine` 统一管控，禁止各端直接 UPDATE 状态字段。

| 值 | 状态 | 允许的下一步 |
| --- | --- | --- |
| 0 | 待接单 | 1 备餐中、5 已取消 |
| 1 | 备餐中 | 2 待取餐、5 已取消 |
| 2 | 待取餐 | 3 配送中、5 已取消 |
| 3 | 配送中 | 4 已完成 |
| 4 | 已完成 | 终态（可进入 6 申诉中） |
| 5 | 已取消 | 终态 |
| 6 | 申诉中 | 4 已完成、5 已取消 |

约束：

1. 状态不可逆跳，非法流转直接抛业务异常。
2. 每次流转写入一条状态流转记录（操作人、时间、变更原因），保证全程可追溯。
3. 抢单使用 Redis 分布式锁保证同一订单同一时刻只有一个写入者。

## 六、AI 能力层的工程约定

- 统一客户端 `modules/ai/client/LlmClient`：负责请求构造、超时、重试、异常降级。
- 提示词模板放在 `resources/prompts/*.md`，业务数据以结构化方式注入，不让模型自行猜测。
- 模型返回统一按 JSON 解析，解析失败走降级逻辑（关键词检索兜底），不把异常抛给前端。
- AI 结果落库时必须记录：来源记录 ID、模型版本、生成时间、校验状态。
- 多轮对话上下文采用滑动窗口，只保留最近 N 轮。

## 七、非功能需求落地要点

| 需求 | 落地方式 |
| --- | --- |
| 普通页面 ≤ 2s，搜索 ≤ 1s | 列表分页 + Redis 缓存热点数据 |
| AI 首响应 ≤ 5s | 流式返回（SSE/WebSocket），超时降级 |
| 并发 ≥ 100 用户 | 无状态服务，Redis 承载热点读与锁 |
| 订单推送 ≤ 2s | WebSocket + 前端轮询兜底双通道 |
| 密码安全 | BCrypt 加盐哈希，禁止明文 |
| 数据脱敏 | 手机号、身份证号返回前端前脱敏 |
| 接口安全 | 拦截器统一解析 Token + 角色校验注解 |
